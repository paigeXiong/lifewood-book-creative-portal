# API 性能与容量基线

`npm run bench:api` 启动独立本地服务，使用合成项目测量读取接口。该工具用于比较相同机器上代码修改前后的表现，不代表生产环境容量或服务承诺。

## 运行

需要 Node.js 22.13+（使用内置 `node:sqlite`）和 .NET 10 SDK / 运行时。先构建后端；已有本地服务运行时使用独立输出目录，避免 Windows 文件占用：

```powershell
dotnet build services/platform-api/Lifewood.PlatformApi.csproj -c Release --artifacts-path C:/Aigc/artifacts/performance-dotnet
npm run bench:api -- artifacts/performance-dotnet/bin/Lifewood.PlatformApi/release/Lifewood.BookPortal.Server.dll
```

不提供 DLL 参数时使用标准 Release 输出。工具不接受服务器 URL 或数据目录，只使用 `127.0.0.1:5097`；端口被占用就退出。每次创建 `artifacts/api-benchmark/<UUID>`，服务数据、备份、协调锁和日志均位于本次目录。通过 API 创建测试账号及模板，停服后扩充合成记录，再启动读取。正常退出、请求失败和 SIGINT / SIGTERM 都会停止本次服务；强制终止整个系统不在该保证内。

不要在构建、其它测试或另外一轮压测同时运行时比较结果。前后版本应使用同一份脚本、同一运行环境，分别保存报告。

## 负载与统计口径

- 数据量分别为 1,000 和 10,000 个项目，90% 属于测量客户、10% 属于另一客户；共两个客户及一个管理员。
- 前 20 条为草稿，其余模拟已提交记录，状态包含新建、制作中和完成。模板有中英文项目名、书名、作者、约 2 KB 简介和 16 个角色描述。
- 合成记录用于读取测试，不模拟完整提交历史、通知、附件二进制或真实用户分布。
- 测量客户列表（20 / 100 条分页）、关键词搜索、统计、单个详情，以及管理员列表与搜索。
- 每场景先预热 5 次，再分别以并发 1 和 8 发出 60 次请求；两个规模合计 1,680 次计时请求（最初六场景版本为 1,440 次）。
- 延迟从发送请求到收到完整响应体，包含本机 HTTP、鉴权、数据库查询与序列化，不含之后的 JSON 解码及断言；传输失败使用失败耗时，超时为 15 秒。
- 报告记录 P50、P95、最大延迟、尝试数、完成数、成功数、传输失败、HTTP 状态分布、成功请求速率和完成响应的平均字节数。分位数采用排序后向上取整的样本位置。
- 每个响应都校验关键业务结果，包含分页总数、条数、搜索命中、详情标识和客户数据隔离；失败会保留报告并以非零状态退出。
- `report.json` 记录 DLL 路径及 SHA-256、脚本 SHA-256、Git HEAD 与工作区状态、.NET 运行时、Node、CPU 和操作系统。每完成一组场景就保存，便于定位中途失败。

这是应用预热后的循环读负载，不是磁盘冷缓存测试。成功请求速率仅是该固定批次的实测速率，不是系统持续吞吐上限。短时写入竞争、上传重放及下载完整性已另见 [混合读写验证](./mixed-load-validation.md)。有节奏的持续保存与 CPU / 内存观察另见 [持续读写与资源监测](./sustained-load-validation.md)；大量连接、GC、真实网络、浏览器渲染及高可用部署仍待测量。

## 已实施的优化

客户列表只读取项目和书籍摘要所需字段，不再读取和反序列化完整创意与配音资料。摘要仍保留原来的字段、占位符、封面选择、排序、分页和权限规则。

新增 `(owner_id, status, workflow_status)` 覆盖索引，让客户统计和草稿计数直接读取较小的索引，减少对大型项目 JSON 所在记录的访问。索引在旧库字段迁移之后创建，重复启动安全；会增加少量数据库空间及写入维护成本。

中英文回归覆盖封面顺序、空字段、旧数据、客户隔离、排序和统计语义。

## 搜索与管理员列表优化

客户执行非空搜索时，使用包含项目名、书名、作者、状态和更新时间的表达式索引，在较小的索引中完成包含匹配。普通浏览的页查询明确使用原更新时间索引，总数统计使用较小的状态索引，避免新索引影响普通列表查询计划。保留原来的 LIKE 行为，包括英文大小写、中文以及 `%` / `_` 通配符，没有切换成分词搜索。

管理员列表使用按实际显示更新时间排序的索引，索引同时包含权限与筛选所需的项目字段。总数统计减少整份项目记录的读取，页查询只加载所需的项目正文；更新时间相同时按项目 ID 排序，保证分页顺序稳定。管理员、运营人员分配范围、停用账号和退回草稿的规则保持不变。

索引由 SQLite 在项目修改、工作流更新、重新分配和删除时自动维护；启动时为已有数据补建，重复启动不重复创建。两个附加索引会增加磁盘占用和写入维护成本。当前读负载结果不代表混合读写能力；后续完成的短时写入竞争与一致性检查见 [混合读写验证](./mixed-load-validation.md)，有节奏的持续负载另见 [资源监测验证](./sustained-load-validation.md)，并非最大吞吐容量测试。
