## 1. 文档目的

本文档用于明确第一阶段前端产品的业务范围、页面结构、交互流程、数据要求、API 对接边界及验收标准，作为产品设计、UI 设计、前端开发和后端接口对接的共同依据。

第一阶段建设面向客户的书籍视频项目资料提交入口。客户填写制作书籍故事视频所需的结构化信息、文件、角色设定、视觉偏好、配音偏好和参考素材，并将项目资料包提交给制作团队。

平台暂不承担视频生成、内部生产管理、客户审片返修和最终成片交付。

## 2. 产品背景

现有视频制作委托通常通过聊天、邮件或网盘分散收集书籍资料、创意要求和参考素材，容易产生以下问题：

- 客户不知道需要提供哪些资料。
- 不同项目提交的信息结构不一致。
- 文件、文字说明和创意偏好分散，制作团队需要二次整理。
- 关键资料缺失时，制作团队需要反复沟通。
- 移动端拍摄或上传参考图片、视频不方便。
- 后端业务和接口尚未完全确定，前端需要支持快速调整对接方式。

本平台通过分步向导引导客户完成资料填写，并将所有信息整理为标准化项目资料包后提交给制作团队。

## 3. 产品目标

### 3.1 核心目标

- 让客户创建书籍视频项目并提交完整项目资料包。
- 通过清晰的步骤和校验机制降低资料遗漏率。
- 将任务整理为统一、结构化的数据与文件包。
- 支持桌面端和移动端填写及上传。
- 支持中英文界面，并为其他语言预留扩展能力。
- 在后端接口频繁调整时，尽量避免修改页面和业务组件。

### 3.2 成功指标

第一阶段建议关注以下指标，具体目标值待业务方确认：

- 新建任务向导完成率。
- 首次提交资料完整率。
- 草稿恢复成功率。
- 文件上传成功率。
- 平均任务填写时长。
- 因资料缺失而退回补充的任务比例。

## 4. 用户与权限

### 4.0 登录系统边界

- 当前平台自带正式账号、密码和会话，不依赖外部登录 API，也不提供假用户选择或 Mock Token。
- 首次运行显示“创建平台负责人账号”，创建成功后所有入口统一改为邮箱与密码登录。
- 不提供默认账号、默认密码或源码内置测试用户；负责人自行设置至少 12 个字符的密码。
- 密码使用 ASP.NET Core `PasswordHasher<TUser>` 哈希后保存于 SQLite，绝不以明文、可逆密文或浏览器存储保存。
- 登录状态使用 HttpOnly、SameSite=Strict Cookie；用户主动选择时才创建持久会话。
- 所有修改类 API 必须校验 CSRF Token；登录和首次建号接口必须限流。
- 同一账号连续登录失败 5 次后锁定 15 分钟，错误提示不得暴露邮箱是否存在。
- 用户与项目、附件通过稳定用户 ID 关联，任何请求不得依赖前端传入的用户 ID 决定数据归属。
- 未来如接入企业 SSO，应替换认证适配层并保持 `CurrentUser` 领域模型与业务页面不变。

### 4.1 第一阶段用户

#### 客户项目提交人

第一阶段正式前端唯一需要完整支持的业务角色。内部人员不通过该前端管理生产工单。

可执行操作：

- 查看本人的项目草稿和项目提交记录。
- 创建书籍视频项目。
- 保存和继续编辑草稿。
- 上传、替换和删除任务文件。
- 预览任务汇总信息。
- 提交项目资料包。
- 查看项目编号、提交时间和受理状态。
- 删除未提交的草稿。

### 4.2 权限原则

- 用户只能访问本人或所属组织有权限查看的任务。
- 草稿可以编辑和删除。
- 项目资料包一旦提交即冻结为不可变快照，第一阶段不提供修改、删除、撤回、复制或再次提交操作。
- 已提交记录只提供项目提交记录和受理状态查询，不提供工单式增删改管理界面。
- 前端权限控制只用于界面展示，最终权限必须由后端校验。

### 4.3 用户资料模型

当前用户身份由平台真实账户系统提供。首期只支持首次负责人建号、邮箱密码登录和只读展示，不建设公开注册、找回密码、资料编辑、昵称修改或头像上传功能。

建议统一用户模型：

| 字段 | 是否必需 | 说明 |
| --- | --- | --- |
| 用户 ID | 是 | 平台生成的稳定唯一标识 |
| 用户名 | 否 | 登录名或账号标识，不一定适合直接展示 |
| 用户昵称 | 是 | 顶部用户菜单、创建人和操作记录中的显示名称 |
| 用户头像 | 否 | 头像 URL 或文件引用 |
| 邮箱 | 否 | 只读联系方式 |
| 所属组织 ID | 否 | 用于任务范围和权限判断 |
| 所属组织名称 | 否 | 界面只读展示 |
| 角色 | 是 | 例如客户项目提交人，具体值由客户系统提供 |
| 权限 | 否 | 精细功能权限，具体协议待对接 |
| 界面语言 | 否 | 用户偏好的 locale |
| 时区 | 否 | 日期和时间显示使用 |

头像规则：

- 账户有真实头像图片时显示该图片；没有真实头像时，由后端根据用户昵称首字母、稳定背景色和高对比字体色生成头像图片资源。
- 前端只能通过 `<img>` 加载头像 URL，不得用 `span`、标签、CSS 圆形背景和普通文字在页面中伪造头像。
- 同一用户的生成头像配色保持稳定；中文取一至两个字符，英文多词名称取首尾单词首字母。
- 头像不是识别用户的唯一方式，账户入口必须显示昵称并提供可交互的账户菜单。
- 不将第三方头像 URL 长期缓存为公开资源。

## 5. 产品范围

### 5.1 第一阶段包含

- 登录后的基础应用框架。
- 我的书籍视频项目（草稿与提交记录）。
- 创建书籍视频项目入口。
- 四步任务创建向导。
- 草稿保存、自动保存与恢复。
- 文件上传、进度显示、失败重试和删除。
- 任务完整性检查。
- 提交确认。
- 提交成功结果页。
- 草稿的保存、恢复、继续填写和删除。
- 已提交项目的记录查看；记录只展示项目编号、提交时间、受理状态和提交快照，不提供编辑操作。
- 中英文国际化。
- 桌面端和移动端响应式适配。
- 统一 API 客户端与错误适配层；客户前端只连接平台正式 API。
- 可随时移除的测试控制台，用于只读检查平台收到的登记资料；它连接同一正式 API 并使用真实账号登录。

### 5.2 第一阶段不包含

- 任何 AI 模型、AI 服务或 AI 推理能力。
- 手稿自动解析、主题提取、角色提取和关键场景提取。
- AI 推荐角色、视觉风格、标签、音色或创意方向。
- AI 实时预览、AI 图片预览和 AI 视频预览。
- AI 脚本、分镜、图片、视频、音乐和配音生成。
- 内部工单管理、设计团队工作台及生产调度。
- 内部 QC、任务分配和生产进度管理。
- 在线脚本审阅和场景编辑。
- 视频时间点评论与返修闭环。
- 最终成片在线播放和下载交付。
- 支付、套餐、订阅和升级。
- 实时聊天或站内沟通。
- 复杂组织、部门和成员管理。
- 可视化表单设计器、字段拖拽编排和管理员自定义表单 Schema。

以上能力可在后续阶段扩展，但不应阻塞当前架构。

### 5.3 AI 能力边界

产品名称和业务资料中可以出现“AIGC”，但本系统本身不提供 AI 能力。系统只负责收集和管理客户填写的项目资料，并把结构化项目资料包提交给制作团队或正式 API。

前端不得出现以下会造成误解的状态或文案：

- “AI 正在分析书籍”。
- “正在提取角色或场景”。
- “正在智能推荐”。
- “正在生成预览”。
- “正在生成脚本、配音或视频”。

视觉风格示例图、角色参考图和参考音色试听均为后台配置的静态参考素材，不是本系统实时生成的结果。

## 6. 信息架构

```text
应用
├── 我的书籍视频项目
│   ├── 全部项目
│   ├── 草稿
│   └── 已提交
├── 创建书籍视频项目
│   ├── 第一步：书籍与项目资料
│   ├── 第二步：角色与视觉风格
│   ├── 第三步：配音与参考素材
│   └── 第四步：确认并提交
├── 项目提交记录
│   ├── 项目摘要
│   ├── 已提交资料
│   └── 当前状态
└── 个人菜单
    ├── 语言切换
    └── 退出登录
```

第一阶段可以不建设独立首页。用户登录后默认进入“我的书籍视频项目”。

## 7. 核心业务流程

```text
进入我的书籍视频项目
  → 创建书籍视频项目
  → 填写书籍与项目资料
  → 配置角色与视觉风格
  → 配置配音并上传参考素材
  → 查看项目资料包与缺失项
  → 确认授权及提交声明
  → 提交给制作团队
  → 显示项目编号与项目提交记录
```

流程要求：

- 用户可以在步骤之间前进和返回。
- 返回上一步不得丢失已填写内容。
- 非关键字段缺失时允许保存草稿。
- 提交前必须完成必填项校验。
- 页面关闭或刷新后应能恢复最近保存的草稿。
- 提交过程中必须阻止重复点击产生重复任务。

## 8. 页面及功能需求

## 8.1 全局应用框架

全局工具栏建议包含：

- 当前模块或必要的返回入口。
- 与当前页面直接相关的任务操作。
- 语言切换。
- 当前用户菜单。

主应用不要求显式展示 Logo。不同页面只呈现完成当前任务所需的上下文；页面标题、页面描述和页面介绍按需选择，不同时常驻展示。

全局要求：

- 所有页面需要明确的加载、空数据、错误和无权限状态。
- 网络异常时提供重试操作。
- 移动端导航应折叠，不得遮挡主要操作。
- 表单中未保存的变更需要在离开页面时给予提示。

## 8.2 我的书籍视频项目

### 8.2.1 页面目标

帮助客户继续项目草稿、创建书籍视频项目，或查看已经提交的项目记录与受理状态。它不是工单管理列表。

### 8.2.2 展示字段

- 任务封面或默认占位图。
- 项目名称。
- 书名。
- 创建时间。
- 最近更新时间。
- 当前状态。
- 项目编号（提交后显示）。

### 8.2.3 状态筛选

第一阶段至少支持：

- 全部。
- 草稿。
- 提交中。
- 已提交。
- 提交失败。

### 8.2.4 用户操作

- 创建书籍视频项目。
- 继续编辑草稿。
- 查看已提交项目的提交记录。
- 删除草稿，删除前二次确认。

已提交项目不显示编辑、删除、复制、撤回或重新提交操作。失败发生在正式提交完成之前时，原记录仍保持草稿属性，客户修正后重新提交；不得把已成功提交的项目改回可编辑状态。

### 8.2.5 空状态

用户没有项目时，展示简短说明和“创建第一个书籍视频项目”按钮。

## 8.3 第一步：书籍与项目资料

### 8.3.1 项目与客户信息

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| 客户名称 | 文本 | 是 | 个人客户可填写作者姓名 |
| 联系人 | 文本 | 是 | 主要对接人 |
| 邮箱 | 邮箱 | 是 | 用于联系和通知 |
| 电话 | 电话 | 否 | 需支持国际区号 |
| 品牌/分支 | 下拉或文本 | 否 | 选项优先由 API 返回 |
| 临时项目名称 | 文本 | 是 | 制作团队后续可正式命名 |
| 视频目标 | 下拉 | 是 | 选项由 API 返回 |
| 截止时间 | 日期 | 否 | 不允许选择已过去日期 |
| 目标受众 | 多选 | 是 | 选项由 API 返回 |

### 8.3.2 书籍信息

| 字段 | 类型 | 是否必填 | 建议限制 |
| --- | --- | --- | --- |
| 书名 | 文本 | 是 | 200 字符 |
| 副标题 | 文本 | 否 | 200 字符 |
| 作者姓名 | 文本 | 是 | 100 字符 |
| 书籍类型 | 下拉 | 是 | 选项由 API 返回 |
| 一句话卖点 | 多行文本 | 是 | 150 字符 |
| 内容简介 | 多行文本 | 是 | 600 字符 |
| 目标语言 | 下拉 | 是 | 与界面语言相互独立 |
| 期望视频时长 | 下拉 | 是 | 选项由 API 返回 |
| 发布平台 | 多选 | 否 | 选项由 API 返回 |

### 8.3.3 文件与源材料

| 文件类别 | 是否必填 | 参考格式 | 参考限制 |
| --- | --- | --- | --- |
| 书籍封面 | 是 | JPG、PNG | 10MB |
| 完整手稿或节选 | 是 | PDF、DOCX、TXT | 200MB |
| 重点章节 | 否 | PDF、DOCX | 50MB |
| 品牌规范 | 否 | PDF | 50MB |
| 授权确认文件 | 视业务规则 | PDF、DOCX | 20MB |
| 补充图片或手机照片 | 否 | JPG、PNG | 单文件 20MB |

文件格式、大小和数量必须由服务端配置或 API 返回。上表仅作为初始默认值，前端不得将其散落硬编码在页面组件内。

上传组件需要支持：

- 点击选择和拖拽上传。
- 移动端相册或相机选择。
- 上传进度。
- 上传取消。
- 失败重试。
- 文件类型及大小校验。
- 已上传文件预览或名称展示。
- 替换和删除。
- 文件上传完成前禁止最终提交。

### 8.3.4 标签与元数据

建议分为：

- 受众标签。
- 内容基调。
- 视频用途。
- 目标市场。
- 内容敏感度。

标签必须通过 API 获取，保存稳定 ID，界面展示对应语言的名称。

## 8.4 第二步：角色与视觉风格

### 8.4.1 角色类型

初始预设：

- 主角。
- 配角。
- 旁白。
- 导师。
- 反派。
- 儿童。
- 背景角色。

角色类型由 API 返回，前端不依赖中文或英文名称判断业务逻辑。

### 8.4.2 角色信息

每个角色支持以下字段：

| 字段 | 是否必填 | 建议限制 |
| --- | --- | --- |
| 角色类型 | 是 | API 选项 |
| 角色名称 | 是 | 80 字符 |
| 故事定位 | 是 | 200 字符 |
| 性格描述 | 是 | 300 字符 |
| 外貌描述 | 是 | 300 字符 |
| 年龄范围 | 否 | API 选项 |
| 性别 | 否 | API 选项，包含不指定 |
| 服装描述 | 否 | 200 字符 |
| 表情或情绪特点 | 否 | 150 字符 |
| 声线提示 | 否 | 100 字符 |
| 参考图片 | 否 | 最多 6 张，具体由 API 配置 |

角色功能要求：

- 可以添加多个角色。
- 可以编辑、删除和调整角色顺序。
- 支持预设角色和自定义角色。
- 删除已有内容的角色时需要二次确认。
- 至少需要一个主要角色，是否强制为“主角”待业务确认。

### 8.4.3 视觉风格

初始预设参考：

- 电影写实。
- 故事书插画。
- 极简编辑风。
- 水彩。
- 3D 动画。
- 高级动态图形。

每个风格选项包括：

- 稳定 ID。
- 多语言名称。
- 多语言描述。
- 缩略图。
- 是否启用。
- 排序值。

用户选择一个主要视觉风格，并可以补充上传风格参考图。

### 8.4.4 风格标签

支持以下可配置标签组：

- 情绪标签。
- 图片风格标签。
- 视频节奏及剪辑风格标签。

允许多选，最大选择数量由 API 配置。

### 8.4.5 参考素材与选择摘要

原型中的“实时预览”不在第一阶段实现。当前页面只展示：

- 管理员上传的角色参考图或默认占位图。
- 后台配置的视觉风格示例图。
- 当前已选角色、视觉风格和标签的文字摘要。

这些内容均不是 AI 生成结果。界面不得使用“实时生成”“AI 预览”等文案。

## 8.5 第三步：配音与参考素材

### 8.5.1 配音偏好与参考音色

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 内容语言 | 是 | 旁白实际使用语言 |
| 旁白语气 | 是 | 例如励志、冷静、权威 |
| 语速 | 是 | 慢、中、快或服务端选项 |
| 发音备注 | 否 | 建议 200 字符 |
| 声音性别 | 否 | 女性、男性、中性、不指定 |
| 声音年龄 | 否 | API 选项 |
| 口音 | 否 | API 选项 |
| 情绪风格 | 否 | API 选项 |
| 参考音色 | 否 | 可选择多个候选项，并指定一个首选项 |
| 自定义音色描述 | 否 | 客户可用文字补充无法通过选项表达的偏好 |

参考音色用于帮助客户表达配音偏好，不代表最终生产时必须使用某个确定音色。制作团队可以结合项目内容、可用资源和客户偏好确定实际配音。

参考音色必须由后台配置并通过 API 动态获取，图片原型中展示的“温暖女声”“自信男声”“沉稳讲述者”和“年轻引导型”等仅为示例，不构成固定枚举或数量限制。

每个参考音色建议包含：

- 稳定 ID。
- 多语言名称与描述。
- 试听音频地址。
- 性别、年龄、语言、口音和情绪等筛选标签。
- 是否推荐。
- 是否启用。
- 排序值。
- 可选的品牌或业务范围限制。

用户可以选择多个参考音色并指定一个首选项，也可以完全不选择，只填写自定义音色描述和发音备注。界面应明确提示：“参考音色仅用于表达偏好，最终效果以制作结果为准。”

开发测试使用平台 API 的隔离数据目录和本地示例音频，不在客户前端中提供 Mock 数据模式。

### 8.5.2 参考素材

| 类别 | 格式参考 | 限制参考 |
| --- | --- | --- |
| 示例视频 | MP4、MOV | 500MB |
| 示例图片 | JPG、PNG | 单张 20MB，最多 10 张 |
| 情绪板 | JPG、PNG | 单张 20MB，最多 10 张 |
| 竞品案例 | 链接、PDF、图片 | 待确认 |
| 场景说明 | PDF、DOCX、TXT | 10MB |
| 必须做/不能做说明 | PDF、DOCX、TXT | 10MB |

竞品案例需要同时支持链接录入和文件上传。

### 8.5.3 创意方向

| 字段 | 是否必填 | 建议限制 |
| --- | --- | --- |
| 核心信息 | 是 | 300 字符 |
| 必须出现的场景 | 否 | 300 字符 |
| 作者偏好 | 否 | 300 字符 |
| CTA 或结尾信息 | 否 | 300 字符 |
| 音乐氛围 | 否 | 200 字符 |
| 敏感或需要避免的内容 | 否 | 200 字符 |

## 8.6 第四步：确认并提交

### 8.6.1 页面目标

在正式提交前汇总全部任务资料，并明确显示缺失项和需要修正的内容。

### 8.6.2 汇总内容

- 项目与客户摘要。
- 书籍信息。
- 文件清单及上传状态。
- 标签。
- 角色列表。
- 已选视觉风格与标签。
- 配音偏好。
- 参考素材。
- 创意方向。

每个区块提供“返回修改”入口，并跳转到对应步骤和字段附近。

### 8.6.3 提交前检查

- 所有必填字段已经填写。
- 必传文件上传成功。
- 不存在仍在上传的文件。
- 服务端校验通过。
- 用户完成授权和真实性确认。
- 用户确认提交后项目资料包永久冻结，正式前端不再提供修改、删除、撤回或重新提交能力。

客户端校验通过后，仍必须调用服务端校验接口；不能只依赖前端校验。

### 8.6.4 防重复提交

- 用户点击提交后立即禁用提交按钮。
- 页面显示明确的提交中状态。
- 请求携带幂等键或由后端提供等效机制。
- 网络超时后先查询提交状态，再决定是否允许重试。

## 8.7 提交结果页

提交成功时展示：

- 成功状态。
- 项目编号。
- 项目名称。
- 提交时间。
- “查看项目提交记录”和“返回我的书籍视频项目”操作。
- 后续流程说明。

提交失败时展示：

- 失败原因的本地化说明。
- 可恢复错误的重试操作。
- 返回草稿继续修改的入口。
- 已成功上传的文件不得要求无条件重新上传。

## 8.8 项目提交记录

项目提交记录不是工单详情或管理页面，只用于确认项目资料包已被接收：

- 受理状态。
- 项目编号。
- 项目及书籍摘要。
- 已提交表单数据。
- 文件列表。
- 提交时间。

项目提交记录页面不得出现编辑、删除、撤回、复制、分派、改状态或生产管理入口。内部生产状态如需展示，前端只显示 API 返回的概括状态，不实现内部工作流。

## 9. 状态模型

第一阶段建议使用以下前端业务状态：

| 状态值 | 中文显示 | 英文显示 | 说明 |
| --- | --- | --- | --- |
| `draft` | 草稿 | Draft | 可以编辑 |
| `validating` | 正在检查 | Validating | 提交前服务端校验 |
| `submitting` | 正在提交 | Submitting | 正在创建正式任务 |
| `submitted` | 已提交 | Submitted | 提交成功，默认只读 |
| `submission_failed` | 提交失败 | Submission failed | 可以查看错误并重试 |
| `cancelled` | 已取消 | Cancelled | 后续可选能力 |

后端可能返回更多生产状态。前端需要通过状态映射表转换，不得在组件中散落状态判断。

## 10. 草稿与自动保存

### 10.1 保存策略

- 用户主动点击“保存草稿”时立即保存。
- 字段发生变化后采用防抖自动保存，建议间隔 1 至 3 秒。
- 切换步骤前触发一次保存。
- 文件上传成功后立即更新草稿中的文件引用。
- 显示“正在保存”“已保存”“保存失败”状态。

### 10.2 本地容错

- API 不可用时，可将未提交的表单快照暂存在浏览器本地。
- 恢复时需要比较本地版本和服务端版本时间。
- 出现冲突时不得静默覆盖，应提示用户选择或保留更新版本。
- 敏感文件内容不得直接持久化在浏览器本地，只保存文件元数据或上传引用。

## 10.3 独立测试工单服务

### 10.3.1 服务定位

开发和测试阶段需要提供一个与工单填写前端独立运行的测试工单服务，用于在正式后端尚未提供或不可访问时，完整验证“保存草稿—上传文件—校验—提交—接收工单”的业务闭环。

该服务属于开发测试设施，不是客户的正式工单系统，也不承担视频生产功能。

### 10.3.2 基本能力

测试工单服务至少需要支持：

- 接收前端创建的任务草稿。
- 保存和更新任务草稿。
- 接收文件上传或保存测试文件的元数据及引用。
- 执行基础必填项校验。
- 接收正式提交操作并生成唯一测试工单编号。
- 查询测试工单列表及详情。
- 查看客户提交的完整表单数据和文件清单。
- 修改测试工单状态，用于验证前端的状态展示。
- 删除单条测试数据。
- 一键清理或重置全部本地测试数据。
- 模拟校验失败、提交失败、超时和无权限等异常场景。

### 10.3.3 测试管理界面

测试服务应提供一个简单、独立的测试管理界面，供开发和测试人员使用。该界面不属于正式工单填写前端设计范围，不要求采用正式产品视觉，但至少支持：

- 查看工单列表。
- 按状态或关键词筛选。
- 查看工单详情和原始提交数据。
- 查看上传文件的元数据。
- 修改工单状态。
- 删除或重置测试数据。
- 触发预设的错误响应场景。

测试管理界面不得复用正式客户权限作为安全保障；它只能在本地或明确隔离的测试环境启用。

### 10.3.4 接口兼容原则

- 工单填写前端调用的业务方法和请求结构应尽量与未来正式 API 一致。
- 测试工单服务应实现前端所需的 API 契约，而不是要求页面针对测试服务编写另一套调用逻辑。
- 切换正式后端时，只替换 API 基础地址或适配器，不修改任务页面。
- 测试服务可以提供额外的管理接口，但这些接口必须与正式工单 API 分离，例如使用独立的 `/test-admin` 路径空间。

### 10.3.5 数据与文件

- 测试数据可以使用本地嵌入式数据库或其他可重置的本地存储。
- 测试文件必须保存到明确的测试目录，不得写入正式存储。
- 本地测试数据不保证长期保留，不可用于保存真实客户的重要资料。
- 清理测试数据时必须限制在测试服务自己的数据目录内。

### 10.3.6 发布隔离

- 测试工单服务及其管理界面必须作为独立工程、独立进程或独立开发依赖运行。
- 正式前端构建不得包含测试工单管理页面、测试管理路由或测试服务代码。
- 正式部署配置不得启动测试工单服务。
- 正式环境不得通过运行时开关、地址参数或隐藏入口启用测试管理能力。
- 测试服务的默认账号、测试密钥、模拟数据和本地文件不得进入正式发布物。
- CI/CD 应分别构建正式前端与测试设施，并对正式发布物执行隔离检查。

## 11. API 可变性设计

## 11.1 设计目标

正式平台 API 已落地。前端仍必须将页面、业务模型和实际 HTTP 接口解耦，使 URL、字段结构或响应格式变化时主要修改适配层。

```text
页面组件
  → 业务服务
  → 领域模型
  → API 适配器
  → HTTP 客户端
  → 正式平台 API
```

## 11.2 分层职责

### 页面组件

- 负责展示和用户交互。
- 不拼接接口 URL。
- 不直接理解后端响应字段。

### 业务服务

提供稳定方法，例如：

```ts
projectService.listProjects(query)
projectService.createDraft(input)
projectService.getProject(projectId)
projectService.saveDraft(projectId, draft)
projectService.validateProject(projectId)
projectService.submitProject(projectId)
projectService.deleteDraft(projectId)

uploadService.upload(projectId, category, file)
uploadService.cancel(uploadId)
uploadService.remove(projectId, fileId)

optionService.getFormOptions(locale)
voiceService.listVoices(query)
```

### API 适配器

- 将后端 DTO 转换为前端领域模型。
- 将前端提交数据转换为后端请求结构。
- 兼容接口版本差异。
- 统一处理分页、空值、枚举值和错误结构。

### HTTP 客户端

- 配置基础地址。
- 注入认证信息。
- 设置超时。
- 处理请求取消。
- 统一错误拦截。
- 注入语言和追踪请求头。

## 11.3 环境切换

前端只配置正式平台 API 的基础地址：

```env
VITE_API_BASE_URL=/api
```

- 本地开发、浏览器 E2E 与正式部署均连接真实平台 API。
- 浏览器 E2E 使用独立端口和独立数据目录，不污染开发或正式数据。
- 不在正式前端保留 `mock`、`hybrid` 或绕过认证的运行模式。

## 11.4 建议接口清单

接口名称和路径为前期建议，最终以后端协议为准。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/projects` | 查询任务列表 |
| POST | `/projects` | 创建草稿 |
| GET | `/projects/{id}` | 查询任务详情 |
| PUT | `/projects/{id}/draft` | 保存完整草稿 |
| PATCH | `/projects/{id}/draft` | 局部保存草稿，可选 |
| DELETE | `/projects/{id}` | 删除草稿 |
| POST | `/projects/{id}/validate` | 提交前服务端校验 |
| POST | `/projects/{id}/submit` | 正式提交项目资料包 |
| GET | `/projects/{id}/submission-status` | 查询提交结果 |
| POST | `/projects/{id}/files` | 创建文件上传 |
| DELETE | `/projects/{id}/files/{fileId}` | 删除任务文件 |
| GET | `/form-options` | 获取标签、枚举和上传限制 |
| GET | `/visual-styles` | 获取视觉风格 |
| GET | `/voices` | 获取可试听声音 |

大文件是否采用分片上传、预签名 URL 或对象存储直传，需要后端确定。前端上传模块应封装传输策略，以便替换。

## 11.5 统一错误模型

前端期望适配为统一结构：

```ts
interface AppError {
  code: string
  messageKey?: string
  fallbackMessage?: string
  fieldErrors?: Array<{
    field: string
    code: string
    messageKey?: string
  }>
  retryable: boolean
  requestId?: string
}
```

页面优先使用 `messageKey` 显示本地化文案；未知错误使用安全的通用提示，并保留 `requestId` 方便排查。

## 12. 前端核心数据模型

以下为领域模型示意，不等同于最终 API DTO：

```ts
interface TaskDraft {
  id: string
  status: TaskStatus
  version: number
  project: ProjectInfo
  book: BookInfo
  files: TaskFile[]
  tags: TaskTags
  characters: CharacterProfile[]
  visualStyle: VisualStyleSelection
  voiceover: VoiceoverSettings
  references: ReferenceAssets
  creativeDirection: CreativeDirection
  confirmations: SubmissionConfirmations
  createdAt: string
  updatedAt: string
}
```

数据模型原则：

- 使用稳定 ID 保存选项，不保存显示文案作为业务值。
- 时间统一使用带时区的 ISO 8601 字符串。
- 文件只保存上传后的文件 ID、访问引用和元数据。
- 草稿带版本号，用于避免并发覆盖。
- 可选字段明确区分未填写、空字符串和空集合。

## 13. 国际化要求

系统必须适配 i18n，首期至少支持：

- 简体中文：`zh-CN`。
- 英文：`en-US`。

### 13.1 文案要求

- 页面文案使用翻译键，不在组件中硬编码中文或英文。
- 表单标题、占位符、按钮、提示、错误信息和空状态全部国际化。
- 文件大小、数字、日期和时间按当前语言格式化。
- 中文和英文文案长度差异不得造成按钮截断或布局溢出。
- 用户填写的书籍内容、角色描述和创意说明保持原文，不自动翻译。
- “界面语言”与“视频内容语言”是两个独立字段。

### 13.2 动态选项

后端动态选项建议返回稳定值和多语言内容，例如：

```json
{
  "id": "cinematic_realism",
  "name": {
    "zh-CN": "电影写实",
    "en-US": "Cinematic Realism"
  }
}
```

如果后端仅按请求语言返回单一文案，前端请求应携带明确的 locale，并在切换语言后刷新动态选项。

### 13.3 API 请求语言

建议统一发送：

```text
Accept-Language: zh-CN
```

不应使用显示文案作为提交枚举值。

### 13.4 路由级语言版本

所有面向用户的页面路由必须包含明确的 locale 前缀，首期使用：

```text
/zh-CN/tasks
/zh-CN/tasks/new/book
/zh-CN/tasks/{taskId}

/en-US/tasks
/en-US/tasks/new/book
/en-US/tasks/{taskId}
```

要求：

- `zh-CN` 与 `en-US` 页面使用同一套组件和业务逻辑，不复制两套页面代码。
- locale 是路由参数，也是当前界面语言的唯一来源。
- 语言切换时替换路由中的 locale 段，并保留当前页面、工单 ID、查询参数和筛选条件。
- 向导编辑期间切换语言不得清空或重置未保存的表单数据。
- 访问根路径 `/` 时，根据用户偏好、最近选择或浏览器语言跳转到支持的 locale；无法判断时使用产品默认语言。
- 访问不支持的 locale 时跳转到默认 locale 的对应页面，并记录诊断信息，不渲染混合语言界面。
- 页面内链接必须通过统一的 locale-aware 路由工具生成，禁止手工拼接语言路径。
- 浏览器刷新、复制链接和直接打开深层链接时，页面语言和路由必须一致。
- API 路径、文件地址、健康检查和机器接口不添加 locale 前缀，通过请求头或参数传递语言。
- 认证回调等非页面技术路由可以不带 locale，但回调完成后必须返回登录前保存的本地化页面。

## 14. 响应式与移动端要求

- 优先保证桌面端完整填写体验。
- 支持常见手机浏览器完成全流程。
- 移动端表单由多列自动调整为单列。
- 主要操作按钮在小屏下保持易触达。
- 文件上传支持相册、文件和设备相机来源。
- 进度步骤在移动端可以缩写，但必须显示当前步骤。
- 不依赖鼠标悬停完成关键操作。
- 表格在移动端改用卡片或横向滚动，不挤压关键字段。
- 页面不得出现不可控的横向溢出。

## 15. 可用性与无障碍要求

- 所有表单控件具有关联标签。
- 错误不仅依赖颜色表达。
- 键盘可以完成主要表单操作。
- 焦点状态清晰可见。
- 弹窗打开后正确管理焦点。
- 图片具有替代文本；装饰图片不被读屏重复朗读。
- 上传和保存状态通过文本或可访问提示反馈。
- 建议以 WCAG 2.1 AA 作为设计参考。

## 16. 安全与隐私要求

- 前端不得在日志中输出手稿内容、Token 或个人敏感信息。
- 文件下载和预览 URL 不应长期公开有效。
- 文件格式和大小必须由前后端双重校验。
- 对用户输入进行安全渲染，避免直接注入 HTML。
- 认证失效时保留安全的本地草稿提示，并引导重新登录。
- 提交前展示授权与资料真实性确认。
- 删除草稿和文件需要明确确认。
- 前端不得将访问控制视为安全边界。

## 17. 性能要求

建议的初始目标：

- 普通网络下首个可交互页面尽快出现。
- 长表单按步骤拆分，避免一次渲染全部复杂组件。
- 图片上传前可生成本地缩略图，但不得改变原文件提交内容。
- 大文件上传不得阻塞表单其他操作。
- 列表和动态选项支持缓存及合理失效。
- 自动保存应防抖并避免重复提交相同内容。

具体性能指标在技术选型后补充。

## 18. 埋点建议

如项目需要产品数据分析，建议预留以下事件：

- 开始创建任务。
- 完成某一步骤。
- 保存草稿成功或失败。
- 上传开始、成功、失败或取消。
- 提交前校验失败。
- 正式提交成功或失败。
- 用户从缺失项跳转回指定字段。
- 语言切换。

埋点不得包含书籍正文、个人敏感信息或文件内容。

## 19. 验收标准

### 19.1 主流程

- 用户可以从任务列表创建任务并完成四步向导。
- 返回前一步、刷新页面或重新进入草稿后，已保存内容仍然存在。
- 必填项缺失时无法正式提交，并能定位到对应字段。
- 所有必传文件上传完成后才能提交。
- 提交成功后显示唯一项目编号。
- 已提交项目可以查看，不能继续编辑。

### 19.2 API 与异常

- 客户门户和管理中心统一通过 API 适配层访问正式平台 API；历史 Mock/测试服务不进入正式运行与发布链路。
- 页面组件不直接调用具体 HTTP 地址。
- 请求失败、超时、无权限和服务端校验错误均有明确反馈。
- 重复点击提交不会创建重复任务。
- API 字段变化可以在适配器中转换，不要求重写页面。

### 19.3 登录与会话安全

- 首次运行可以创建且只能创建一个平台负责人账号，之后首次设置入口自动关闭。
- 登录、退出、会话恢复、账号锁定和 CSRF 失败均有明确且已国际化的反馈。
- 发布物中不包含测试账号、默认密码、假头像、Mock Token 或绕过认证的开关。
- 退出后原会话不可继续读取用户信息或项目数据。
- AOT 发布形态必须与普通构建使用完全相同的真实认证实现。

### 19.4 可移除测试控制台

- 测试控制台读取平台 API 中的真实登记数据，不再运行独立 Mock 工单服务。
- 控制台必须使用与客户前端相同的真实账号和 Cookie 会话，不得提供用户切换卡片或假登录。
- 控制台首期只用于只读核对表单和文件，不扩大客户登记产品的业务范围。
- 控制台目录和启动项保留明确的“可移除”标记，移除后不影响客户前端与正式 API。

### 19.5 国际化

- 用户可以在中文和英文之间切换。
- 切换语言后静态和动态界面文案正确更新。
- 表单数据不会因为切换语言丢失。
- 中文和英文下均不存在明显文字截断和布局错乱。
- 所有用户页面均具有带 locale 前缀的可直接访问路由。
- `/zh-CN/...` 始终显示中文界面，`/en-US/...` 始终显示英文界面。
- 切换语言后保持当前业务页面、资源 ID、查询参数和未保存表单状态。
- 不支持的 locale 能安全回退到默认语言，不出现循环跳转。

### 19.6 响应式

- 桌面端和常见手机尺寸均可完成任务创建与提交。
- 移动端可以调用系统文件选择器、相册或相机上传素材。
- 小屏下不存在阻塞关键操作的横向溢出。

## 20. 建议实施顺序

1. 建立前端基础工程、设计令牌、路由和 i18n。
2. 定义领域模型、API 适配层和隔离测试数据。
3. 实现任务列表及草稿创建。
4. 实现第一步书籍与项目资料及上传组件。
5. 实现第二步角色与视觉风格。
6. 实现第三步配音与参考素材。
7. 实现确认、校验和提交结果。
8. 完成响应式、异常场景、无障碍和双语检查。
9. 接入真实 API 并完成联调。

## 21. 待确认事项

当前真实账号、平台 API 和提交链路已经落地。以下业务事项不阻塞继续开发，但需要在正式运营前确认：

1. 客户和作者是否为同一种账号角色。
2. 是否允许一个账号属于多个品牌或组织。
3. 是否需要负责人邀请更多真实账号，以及各账号的数据共享边界。
4. 任务提交后能否撤回或补充材料。
5. 授权确认是勾选声明，还是必须上传签署文件。
6. 必填的文件类别及每类文件的最终限制。
7. 大文件采用普通上传、分片上传还是对象存储直传。
8. 参考音色试听数据由哪个服务或后台提供。
9. 动态标签、风格和参考音色由哪个系统维护。
10. 项目名称由客户填写后沿用，还是内部团队必须重新命名。
11. 是否展示内部制作中的概括状态。
12. 是否需要补充官方字体授权或自托管字体文件。
13. 首期英文地区采用 `en-US` 还是原型中的 `en-GB`。
14. 正式部署使用的 TLS 终止代理地址，用于配置 `Network:TrustedProxies`。

## 22. 已确认的产品决策

截至 v0.11，以下内容已确认，不再作为开放问题：

1. 第一阶段建设客户使用的书籍视频项目资料填写与提交前端，不是管理员工单管理系统。
2. 音色定位为客户表达偏好的“参考音色”，由后台配置并通过 API 动态获取，不是前端固定枚举，也不等同于最终生产音色。
3. 平台自带正式账号、密码与 Cookie 会话，不依赖外部登录 API。
4. 首次使用由负责人创建真实账号，仓库和发布物不携带默认账号或密码。
5. 客户前端和可移除测试控制台共用同一真实认证，不允许假身份、Mock Token 或认证降级。
6. 平台正式 API 自行保存登记、附件和提交记录，不依赖独立测试 API。
7. 可以保留简单的可移除测试控制台，但它只读连接正式 API，不实现独立业务数据或假登录。
8. 客户项目提交前端采用 React、TypeScript 和 Vite。
9. 平台正式 API 采用 C#、.NET 10、ASP.NET Core Minimal API、Native AOT 和 SQLite。
10. 平台正式 API 不使用 EF Core，采用 `Microsoft.Data.Sqlite` 和显式 SQL 数据访问，以保证 Native AOT 兼容性。
11. 平台正式 API 的全部代码、依赖、认证、序列化、校验、数据访问和构建流程都必须满足 Native AOT 限制，具体约束见 `docs/technical-architecture.md`。
12. 客户项目提交前端采用 Lifewood 公司配色，但不要求显式展示 Logo，具体视觉令牌、页面布局、组件和响应式规范见 `docs/ui-design-specification.md`。
13. UI 采用紧凑型工具界面，不保留大量空白；每个页面只展示当前任务需要的上下文，标题、描述和介绍按需出现。
14. 普通编辑框必须设置与内容长度匹配的最大宽度，仅大段文字输入使用宽版或全宽编辑区。
15. 用户页面通过 locale 路由前缀区分语言版本，首期为 `/zh-CN/...` 和 `/en-US/...`，两种语言共用页面组件和业务逻辑。
16. UI 图标优先从 `C:\Users\11915\Pictures\svg图标` 选择；本地缺失的图标可以从 [iconfont](https://www.iconfont.cn/) 下载 SVG 后纳入项目，不建立运行时外部依赖。
17. 用户资料由平台真实账户系统提供，前端统一支持用户 ID、昵称、可选真实头像、组织、角色、语言和时区等信息；首期只读展示，不建设用户资料编辑功能。
18. 部分 UI 卡片可以参考 [Lifewood 官网](https://lifewood.com/) 的纸色/白色表面、深绿细边界、圆角和信息层级，但必须适配紧凑型管理员工具，不照搬营销页面的大尺寸留白、超大编号和长篇说明。
19. 第一阶段完全不实现 AI 能力，只提供项目资料的填写、草稿、上传、校验、提交和项目提交记录。
20. 正式客户前端不提供已提交项目的增删改管理；内部工单管理仅可存在于独立测试设施或未来独立内部系统。
21. 创建项目流程采用品牌化项目资料提交体验：通过封面、角色参考、视觉风格示例、参考音色、阶段说明和提交后流程体现服务品质；“我的书籍视频项目”保持紧凑，但不呈现后台管理语义。
22. 品牌化内容必须与当前步骤和真实服务流程直接相关，不增加落地页式 Hero、无业务作用的宣传卡或虚构 AI 能力。
23. 已成功提交的项目资料包是不可变快照。客户只能查看项目提交记录与受理状态，第一阶段不支持编辑、删除、撤回、复制、补交或重新提交。
24. 第一阶段不建设站内通知中心，也不发送邮件或短信通知；项目状态与最终成品通过项目页面查询。
25. 没有真实头像时，后端生成包含昵称首字母、稳定背景色和字体色的实际图片响应，前端不得使用 HTML 标签拼装头像。

## 23. 后续阶段预留

架构上可以为以下能力保留路由和模块扩展空间，但第一阶段不实现：

- 脚本与场景审阅。
- 配音复核。
- 时间点评论。
- 返修材料上传。
- 版本历史。
- 场景级批准。
- 最终成片批准与下载。
- 内部制作状态的详细追踪。

预留是指保持模块边界和数据模型可扩展，不代表第一阶段提前开发不可见功能。
